# 一、项目基本信息

项目名称：

《高性价比数码产品测评聚合与比价系统设计与实现》

实际网站名称：

「极客比价」

项目定位：

这是一个面向普通消费者的数码产品信息聚合、专业测评、用户评价、多平台价格比较、历史价格分析、产品横向对比以及个性化推荐系统。

项目目标：

1. 完成一个真正可以运行的完整 Web 项目。
2. 用户端、管理后台、后端 API、MySQL 数据库必须完整联调。
3. 项目整体达到本科毕业设计的完整度。
4. 项目界面具有现代化科技产品网站的视觉效果。
5. 项目必须方便后续撰写毕业论文。
6. 必须包含具有一定算法含量的“产品性价比评分算法”和“个性化推荐算法”。
7. 项目不能只是静态页面或 Demo，所有核心功能都必须连接真实后端 API 和数据库。
8. 必须提供完整初始化数据，使项目部署后可以直接演示。
9. 必须能够在云服务器上部署。
10. 不允许为了追求所谓商业级复杂度而引入不必要的技术和第三方服务。

==================================================
# 二、核心开发原则
==================================================

这是一个本科毕业设计项目。

请始终遵循：

“功能完整 > 技术炫技”
“稳定运行 > 复杂架构”
“可维护性 > 过度封装”
“论文可解释 > 黑盒算法”
“真实可运行 > 伪代码”

如果一个功能可以用简单可靠的方式实现，就不要过度设计。

# 十九、性价比评分算法
==================================================

这是毕业设计的核心算法之一。

必须真正实现，不允许写死一个数字。

核心思想：

根据：

- 产品性能
- 产品功能
- 用户评分
- 当前价格
- 历史价格
- 品类特点

计算产品性价比。

不同产品类别允许使用不同评价维度。

例如手机可以包含：

性能
屏幕
影像
续航
功能
用户评价
价格

游戏本可以包含：

CPU
GPU
屏幕
散热
内存
存储
用户评价
价格

必须设计合理的标准化方法。

所有指标最好归一化到：

0～100

然后进行加权计算。

例如：

性能得分
功能得分
用户评分
价格优势

最终：

ValueScore = 加权综合评分

注意：

不要简单地：

“性能 / 价格”

就结束。

必须考虑多维指标。

# 二十、价格优势算法
==================================================

价格优势可以参考：

当前价格
历史最低价
同类产品平均价格
同类产品价格区间

例如：

价格越接近历史最低价格：

价格优势越高。

价格低于同类产品平均价格：

价格优势提高。

价格明显高于同类产品：

价格优势降低。

最终标准化到：

0～100。

# 二十二、推荐算法
==================================================

实现：

“基于用户行为 + 产品标签 + 价格区间 + 产品分类 + 性价比评分的混合推荐算法”

推荐因素至少包括：

1. 用户浏览行为
2. 用户收藏行为

5. 产品标签
6. 用户常浏览价格区间
7. 产品性价比
8. 产品热度
9. 产品新鲜度

推荐流程：

用户行为
↓
用户兴趣特征
↓
产品特征
↓
计算匹配度
↓
结合性价比
↓
结合热门度
↓
最终推荐分数
↓
生成推荐列表

例如：

RecommendationScore =

分类匹配度 × 权重
+
标签匹配度 × 权重
+
价格匹配度 × 权重
+
性价比 × 权重
+
热度 × 权重
+
新鲜度 × 权重

必须：

- 进行归一化
- 防止单一指标完全决定结果
- 支持无行为用户

# 四十五、开发过程中的强制规则
==================================================

规则 1：

不要一次性盲目生成整个项目。

必须阶段化开发。

规则 2：

每完成一个重要阶段：

必须运行编译/构建。

规则 3：

发现错误：

优先自己分析和修复。

不要遇到普通编译错误就停止。

规则 4：

不要生成大量“TODO”。

核心功能必须真正实现。

规则 5：

不要使用伪代码。

例如：

// TODO 实现推荐算法

这种方式不允许。

规则 6：

不要为了减少工作量把核心功能改成假数据。

初始化数据可以是模拟数据。

但业务逻辑必须真实运行。

规则 7：

不要删除已有功能来解决新功能问题。

修改代码前先理解现有结构。

规则 8：

如果项目已经存在文件：

先检查。

不要直接覆盖整个项目。

规则 9：

不要随意更换技术栈。

规则 10：

不要擅自删减核心需求。

如果确实发现需求存在技术冲突：

先分析最合理的解决方案。
