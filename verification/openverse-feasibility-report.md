## 1. Openverse API 是否可访问

**否 —— 不可访问（网络层阻断，非域名错误、非限流）**

逐层诊断结果：

| 层级 | `api.openverse.org`（主域名） | 判定 |
|---|---|---|
| DNS 解析 | ✅ 成功 → `128.242.240.212` / `2a03:2880:f10e:83:face:b00c:0:25de` | 域名正确、能解析 |
| TCP 443 连接 | ❌ **连接超时**（8004ms 无响应） | 网络层不通 |
| TLS 握手 | ❌ **握手超时**（8019ms） | 无法建立加密通道 |
| HTTPS GET | ❌ `curl: (28) Connection timed out after 20011 milliseconds` | 请求无法发出 |

curl 详细输出：
```
*   Trying [2a03:2880:f10e:83:face:b00c:0:25de]:443...
*   Trying 128.242.240.212:443...
* Connection timed out after 20011 milliseconds
curl: (28) Connection timed out after 20011 milliseconds
```

**关键判据：DNS 正常但 TCP 不通 ⇒ 属网络出口阻断/策略问题，不是域名写错、不是 API 限流、不是 401/403 鉴权问题。**

### 对照组（排除"整机断网"的可能）

| 域名 | TCP 443 | TLS | HTTPS |
|---|---|---|---|
| `commons.wikimedia.org`（本项目现用源） | ✅ 238ms | ✅（curl 实测 200） | ✅ **200 OK** |
| `wordpress.org` | ✅ 531ms | ✅ TLSv1.3 | — |
| `api.openverse.engineering`（旧域名） | ✅ 179ms | ✅ TLSv1.3 | ⚠️ **301** |

⇒ **本机网络是通的**，能正常访问 Wikimedia 等站点；**唯独 Openverse 不通**。这排除了"环境整体离线"的解释。

### 旧域名也无效（已核实）

`api.openverse.engineering` 确实能连上（TCP+TLS 均成功），返回 **301 Moved Permanently**，但重定向目标正是不可达的主域名：

```
HTTP/1.1 301 Moved Permanently
Location: https://api.openverse.org/v1/images/?q=phone&page_size=3
```

⇒ 绕不过去。这条线索已排除。

## 最终结论

# **C. 当前环境不可验证（对应你的判定：不可验证 → 不建议继续）**

更精确地说，是 **C 的加强版**：

1. **本轮无法验证** —— API 完全不可达，没能取得任何一条候选数据，因此**不能得出"匹配效率太低"的技术结论**（没有样本）。
2. **但就"能否提高覆盖率"这一目标而言，结论是明确的：不能。** 一个连不上的数据源，无论其内容多好，对本项目的覆盖率贡献都是 **0**。
3. **不要等待、不要折腾网络** —— DNS 正常而 TCP 不通，属于出口策略层阻断，不是靠重试、加 token、换参数能解决的。按你的要求，我没有改 DNS、没有装代理、没有反复重试。

### 因此对当前覆盖率问题（40/132）的建议

Openverse 这条路**本轮走不通**，不应作为提升覆盖率的方案。既然核心痛点是"132 个产品中仍有大量灰色占位图"，更现实的方向是：

- **路径 1（本次已完成，代价最低）**：接受上一轮已产出的 15 条候选（1 EXACT + 14 SERIES），可把真实图从 40 提到 **55**（覆盖率 40/132 → 55/132，约 41.7%）。
- **路径 2**：放宽到"类别占位图"——对确实无实拍图的产品，用**同类别**的开放许可通用图（如"机械键盘"通用图），并在前端**明确标注为示意图**而非产品实拍。这是唯一能接近 100% 覆盖且不造假的做法。
- **路径 3**：更换网络环境（或在可访问 Openverse 的机器上）再跑一次本轮验证。若能连通，Openverse 聚合了 Flickr 等大量 CC 内容，**有机会**补充一批（但未经实测，不能承诺）。
